# AIHealth 项目执行协作约定

> 本文档是项目版约定。
> 通用母版见：
> [2026-04-21-agent-execution-collaboration-agreement.md](./2026-04-21-agent-execution-collaboration-agreement.md)
>
> 两者关系：
> - 通用版负责“怎么协作”
> - 项目版负责“AIHealth 里怎么落地”

## 目的

这份约定用于降低主线程上下文过载带来的判断漂移风险，并固定 AIHealth 的默认执行方式。

适用范围：

- `family-doctor` 相关设计、实现、测试、review、CI、handoff
- 后续阶段规划与执行

## 核心原则

默认采用：

- 主线程负责总控、边界、架构、验收、集成、文档状态
- subagent 负责局部实现、专项排查、局部 review、测试补齐

目标不是让主线程“知道得越少越好”，而是让主线程只保留高价值、长期有效的上下文，把高噪声、易过期、可局部闭环的工作交给 subagent。

## 主线程职责

主线程默认负责以下事项：

1. 维护当前阶段目标
2. 维护架构边界和安全边界
3. 决定任务拆分与优先级
4. 指派 subagent 的任务范围与写入边界
5. 审核 subagent 返回结果
6. 做最终实现取舍与集成
7. 跑最终验证并给出阶段结论
8. 维护关键文档、PR 状态、handoff 状态

主线程默认不深陷以下高噪声工作，除非任务很小或必须串行完成：

- 大量局部代码实现
- 大量 review comment 逐条处理
- CI 日志长链路排查
- 文档细节性修订
- 测试细碎补齐

## 主线程保留上下文

主线程默认只长期保留这 4 类上下文：

1. 项目当前阶段与目标
2. 已确认的架构/安全/数据边界
3. 当前分支、PR、CI、merge 状态
4. 下一阶段任务拆分与优先级

以下内容默认不长期驻留在主线程里：

- 长日志
- 冗长 review comment 原文
- 局部实现细节
- 一次性排查过程
- 已验证结束的短期背景

## Subagent 适用场景

以下任务默认优先交给 subagent：

1. 独立代码实现
2. 定点测试补齐
3. 局部 review thread 核对与修复
4. 某个 CI/job 的失败原因调查
5. 局部文档整理
6. 局部重构
7. 只读型代码审查

满足以下条件时，优先使用 subagent：

- 范围清晰
- 写入边界清晰
- 与其他任务依赖较弱
- 可以独立返回可验证结果

## Subagent 返回格式

subagent 返回内容应尽量压缩为结构化结果，至少包含：

1. 做了什么
2. 改了哪些文件
3. 跑了什么验证
4. 结果如何
5. 还剩什么风险或未解决项

主线程不要求 subagent 回传完整过程日志，除非该日志本身就是证据。

## 默认执行顺序

对于多步任务，默认顺序为：

1. 主线程确认目标与边界
2. 主线程拆 task
3. subagent 执行局部任务
4. 主线程收敛结果
5. 主线程做 review / integration
6. 主线程跑最终验证
7. 主线程更新文档、PR、handoff

## 何时不适合下放

以下情况主线程优先直接处理：

1. 架构边界尚未明确
2. 一个决定会影响多个后续阶段
3. 风险高但任务边界不清
4. 多个任务写入同一小片代码且强耦合
5. 需要立即基于最新结果连续做判断

## 当前项目默认策略

对 AIHealth 项目，后续默认采用：

- 规划：主线程主导
- 实现：尽量 subagent 化
- review triage：尽量 subagent 化
- CI 排查：尽量 subagent 化
- 最终验收：主线程负责
- PR / merge / handoff：主线程负责

## 执行目标

这套约定的目标是：

- 降低主线程上下文污染
- 提高判断稳定性
- 提高并行推进效率
- 保持架构与安全边界一致
- 降低中断后恢复成本

## 备注

如果后续发现：

- 主线程仍然过载
- subagent 结果整合成本过高
- 文档和实现脱节

则优先调整任务拆分粒度，而不是回到“所有事情都堆在主线程”的方式。
